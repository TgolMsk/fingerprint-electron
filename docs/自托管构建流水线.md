# 自托管 Runner 构建与草稿发布

本文说明如何用 GitHub Actions 工作流 [`.github/workflows/build-runtime.yml`](../.github/workflows/build-runtime.yml)，在维护者自己的 Windows x64 构建机上执行 [构建迁移与发布](构建迁移与发布.md) 中的锁定流程，并把 `release-set` 的输出创建为 **草稿** GitHub Release。工作流只调用 `fp-kernel/scripts/release.py`，不修改锁定清单、补丁、`VERSION` 或源码；不推送代码、不直接创建标签、不公开发布，草稿由维护者审核后手动发布。

GitHub 托管 runner 只有 4 个 vCPU、约 14 GB 可用磁盘、单个作业 6 小时上限，不足以完成 Chromium/Electron 全量编译，因此只支持自托管 runner。

## 1. 流程概览

工作流只能手动触发（`workflow_dispatch`），同一时间只运行一个（并发组 `fp-kernel-runtime-build`，后到的运行排队；同组已有排队运行时，较早排队的会被 GitHub 取消）。包含五个作业，全部运行在带 `fp-kernel-builder` 标签的同一台构建机上：

| 作业 | 内容 |
| --- | --- |
| `check-tag` | 编译前校验 `release_tag` 格式与锁定清单版本；`draft_release=true` 时确认标签和 Release（含草稿）均未被占用。几秒钟完成，是除 `release` 外唯一拿到 `contents: write` 令牌的作业 |
| `build` | 校验输入与仓库变量 → 预检 → `doctor` → `prepare` → `build` → `package` → `verify-package` → `validate-release` → `release-set` → 生成发布说明；失败时执行 `status` 打印日志尾部。只有只读令牌 |
| `reports` | 上传小型报告为工作流 artifact（保留 30 天）；`draft_release=false` 时另上传完整发布集合（保留 14 天） |
| `release` | 复核 `SHA256SUMS`，再次确认标签未被占用，`gh release create --draft`，核对上传的资产名称与大小 |
| `cleanup` | 仅在 `keep_workspace=false` 且前面全部成功时，删除本次使用的构建工作区 |

创建 Release 放在单独作业中，是因为 `GITHUB_TOKEN` 最长只有 24 小时有效，而完整的在线准备加编译可能超过这个时间；新作业会得到新令牌。后续作业读取的是 `build` 作业留在本机磁盘上的文件，所以必须在同一台机器上运行，工作流会比对 runner 名称，不一致时失败。

工作流实际执行的命令如下，`--lock` 固定为检出的 `fp-kernel/build/lock.json`，方括号内的参数仅在对应变量或条件存在时添加：

```powershell
python fp-kernel/scripts/release.py --lock fp-kernel/build/lock.json doctor --windows-toolchain $Toolchain [--windows-sdk $Sdk] --output <attempt>\reports\doctor.json
python fp-kernel/scripts/release.py --lock ... prepare --workspace <build> --windows-toolchain $Toolchain [--windows-sdk $Sdk] [--reference $Reference] [--depot-tools $DepotTools] [--resume]
python fp-kernel/scripts/release.py --lock ... build --workspace <build> --windows-toolchain $Toolchain [--windows-sdk $Sdk] --jobs <jobs>
python fp-kernel/scripts/release.py --lock ... package --build-dir <build>\src\out\FPTesting --output <attempt>\artifacts
python fp-kernel/scripts/release.py --lock ... verify-package --archive <attempt>\artifacts\fp-electron-44.4.5-fp0.1.0-win32-x64-testing.zip
python fp-kernel/scripts/release.py --lock ... validate-release --archive <同上 ZIP> --workspace <attempt>\validation
python fp-kernel/scripts/release.py --lock ... release-set --archive <同上 ZIP> --output <attempt>\release
# 失败时：
python fp-kernel/scripts/release.py --lock ... status --workspace <build>
```

`FPTesting` 和 ZIP 名称均由锁定清单决定；工作流在 `package` 之后从输出目录查找唯一的 `fp-electron-*.zip`，并核对它与锁定清单推导的名称和 `.sha256` 一致。

目录布局（`FP_WORK_ROOT` 为仓库变量，`<run id>` 是运行 URL `/actions/runs/<run id>` 中的数字）：

```text
<FP_WORK_ROOT>\<run id>\build                         release.py 构建工作区（默认保留，可续跑或作缓存）
<FP_WORK_ROOT>\<run id>\attempt-<n>\validation        validate-release 工作目录
<FP_WORK_ROOT>\<run id>\attempt-<n>\artifacts         package 输出：ZIP、.sha256、.manifest.json、.validation.json
<FP_WORK_ROOT>\<run id>\attempt-<n>\release           release-set 输出，即草稿 Release 的全部资产
<FP_WORK_ROOT>\<run id>\attempt-<n>\reports           上传为 artifact 的小型报告
<FP_WORK_ROOT>\<run id>\attempt-<n>\release-notes.md  草稿 Release 的说明
```

`release.py` 要求验收目录和发布目录必须是新目录，所以同一运行的每次重试（attempt）使用新的 `attempt-<n>`，构建工作区则在重试间共用。

## 2. 构建机要求

硬件：Windows x64，建议 16 核以上、32 GB 以上内存。参考记录为 i5-14600K、48 GB 内存，编译约 3 小时，不含源码准备。`FP_WORK_ROOT` 所在的 NTFS 卷需要数百 GB 可用空间；预检低于阈值（默认 250 GB）时给出警告。

`doctor` 会逐项核对锁定版本，版本不同即失败：

| 工具 | 锁定版本 | 说明 |
| --- | --- | --- |
| Python | 3.14.5 | 用 python.org 安装包为所有用户安装并加入 PATH；不要依赖 Microsoft Store 的 `python` 别名 |
| Node.js | 22.23.2 | `doctor` 与 `validate-release` 都需要 |
| Git | 2.55.0.windows.5 | Git for Windows |
| MSVC / Windows SDK | VS2026 工具集 14.50.35717 / 10.0.26100.0 | 目录结构见 [构建迁移与发布](构建迁移与发布.md) 第 3 节 |
| GitHub CLI `gh` | 任意较新版本 | 仅 `draft_release=true` 需要；托管 runner 预装，自托管需自行安装，例如 `winget install --id GitHub.cli -e --scope machine` |

以上以 `fp-kernel/build/lock.json` 的 `toolchain` 为准。工作流步骤使用系统自带的 Windows PowerShell 5.1，不需要安装 PowerShell 7。每个步骤以 `powershell -NoProfile -NonInteractive -ExecutionPolicy Bypass` 启动：Windows 10/11 客户端默认执行策略为 `Restricted`，runner 默认的 `powershell` shell 在这种机器上会在第一个步骤就报“running scripts is disabled on this system”。`Bypass` 只作用于该步骤进程，不修改机器策略，也不需要为此执行 `Set-ExecutionPolicy`；只有组策略强制了执行策略时，才需要由管理员调整。`-NoProfile` 使服务账号的 PowerShell 配置文件不影响作业。

启用长路径（管理员 PowerShell，重启后生效），否则预检给出警告，Chromium 深层路径可能失败：

```powershell
New-ItemProperty -Path 'HKLM:\SYSTEM\CurrentControlSet\Control\FileSystem' -Name LongPathsEnabled -Value 1 -PropertyType DWord -Force
```

`validate-release` 的字体断言依赖本机已安装的字体，构建机的字体与语言环境应与原验收机器一致。实时杀毒扫描会明显拖慢编译；是否为构建目录设置排除，由机器所有者按安全策略决定。

## 3. 注册自托管 runner

1. 打开仓库 **Settings → Actions → Runners → New self-hosted runner**，选择 Windows、x64。页面给出 runner 下载地址和一次性注册令牌（约 1 小时有效）。
2. 在构建机上为 runner 建立专用的本地标准用户（例如 `fpbuild`），不要使用管理员或个人日常账号。给该账号工具链、缓存目录和 `FP_WORK_ROOT` 的读写权限，并以该账号安装或确认上面的工具在 PATH 中。
3. 按页面命令下载并解压到短路径（例如 `C:\actions-runner`，不含空格和中文），然后配置：

   ```powershell
   cd C:\actions-runner
   .\config.cmd --url https://github.com/TgolMsk/fingerprint-electron --token <页面上的注册令牌> --name fp-builder-01 --labels fp-kernel-builder --work _work
   ```

   询问是否作为服务运行时回答 `Y`，服务账号填 `.\fpbuild`，密码在提示中输入，不要写进命令行。runner 会自动带 `self-hosted`、`Windows`、`X64` 标签，加上 `fp-kernel-builder` 后即与工作流的 `runs-on: [self-hosted, Windows, X64, fp-kernel-builder]` 匹配。
4. runner 配置时把当时的 PATH 记录在 `C:\actions-runner\.path`，作业使用这个值。以后安装或升级 Python、Node.js、Git、`gh`，需更新该文件（或重新配置）并重启服务：

   ```powershell
   Get-Service 'actions.runner.*' | Restart-Service
   ```

5. 在 Runners 页面确认状态为 **Idle**。

**服务模式与桌面会话。** 以服务运行时，进程位于没有交互桌面的 Session 0。`package` 的版本探测和 `validate-release` 的四组验收都会启动 Electron（窗口隐藏，部分用例截图）。已有验收记录均在已登录的桌面会话中完成，**服务模式下尚未实测**。如果在服务模式下验收失败（截图为空、GPU 初始化失败、超时等），先停止服务，改为在服务账号已登录的桌面中运行 `C:\actions-runner\run.cmd`（可配合自动登录和登录时启动的计划任务）；不要修改验收脚本或报告。

**只保留一台带 `fp-kernel-builder` 标签的 runner。** 需要多台构建机时，为每台增加独立标签，并复制工作流改用该标签；否则 `reports`、`release`、`cleanup` 可能被分配到没有构建文件的机器而失败。

## 4. 仓库变量

在 **Settings → Secrets and variables → Actions → Variables** 新建仓库变量，或使用：

```powershell
gh variable set FP_WORK_ROOT --body 'E:\fp-ci' --repo TgolMsk/fingerprint-electron
```

这些都是构建机本地路径，不是机密，放在 Variables 而不是 Secrets。

| 变量 | 必需 | 用途 | 示例 |
| --- | --- | --- | --- |
| `FP_WORK_ROOT` | 是 | 每次运行的工作根目录。必须已存在、位于大容量 NTFS 卷，不能是盘符根目录；不能含空格、中文等非 ASCII 字符（Chromium/depot_tools 不支持）、方括号或 `& \| < > ^ % ! "`；必须在仓库检出目录和 runner 的 `_work` 目录之外（`_work\_temp` 在每个作业开始和结束时被清空） | `E:\fp-ci` |
| `FP_WINDOWS_TOOLCHAIN` | 是 | `--windows-toolchain`：含 `VC\Tools\MSVC\14.50.35717` 的 VS 目录，或合并工具包（可含空格） | `E:\toolchains\vs2026` |
| `FP_WINDOWS_SDK` | 否 | `--windows-sdk`：VS 与 SDK 分开安装时指向 `Windows Kits\10`（可含空格） | `C:\Program Files (x86)\Windows Kits\10` |
| `FP_REFERENCE_CACHE` | 否 | `use_cache=true` 时作为 `--reference`：已有构建根目录，其 `src` 子目录是 Chromium 检出；不能含空格、方括号或非 ASCII 字符 | `E:\fp-ci\12345678901\build` |
| `FP_DEPOT_TOOLS_CACHE` | 否 | `use_cache=true` 时作为 `--depot-tools`：已引导的 depot_tools（含 `python3_bin_reldir.txt`）；不能含空格、方括号或非 ASCII 字符 | `E:\tools\depot_tools` |
| `FP_MIN_FREE_GB` | 否 | 预检可用空间的警告阈值，默认 `250` | `400` |

缺少必需变量、路径不存在或格式不对时，第一个步骤就以 `::error::` 说明原因并停止，不会进入编译。

`FP_REFERENCE_CACHE` 最好与 `FP_WORK_ROOT` 位于同一卷：Git 本地克隆可以硬链接对象，跨卷则完整复制。缓存目录不能位于本次构建根目录内，也不能包含它。保留下来的 `<FP_WORK_ROOT>\<run id>\build` 可以直接作为下一次的 `FP_REFERENCE_CACHE`；缓存只提供 Git 对象和下载依赖，不复用 `out/`（见 [构建迁移与发布](构建迁移与发布.md) 第 3 节）。

## 5. 触发构建

网页：**Actions → Build FP runtime (self-hosted) → Run workflow**，选择分支并填写输入。命令行：

```powershell
gh workflow run build-runtime.yml --repo TgolMsk/fingerprint-electron --ref main `
  -f release_tag=v44.4.5-fp0.1.0-testing.2 -f jobs=16 -f use_cache=true -f draft_release=true -f keep_workspace=true
gh run list --workflow build-runtime.yml --repo TgolMsk/fingerprint-electron --limit 5
gh run watch <run id> --repo TgolMsk/fingerprint-electron
```

| 输入 | 默认 | 说明 |
| --- | --- | --- |
| `release_tag` | 必填 | `v<Electron>-fp<FP Kernel>[-后缀]`（与已发布的 `v44.4.5-fp0.1.0-testing.1` 一致），两个版本必须与锁定清单的 `runtime.electron`、`runtime.fpkernel` 一致；同一版本重新发布递增后缀，如 `v44.4.5-fp0.1.0-testing.2`。已存在同名标签或 Release（含草稿）时，由 `check-tag` 在编译前拒绝 |
| `jobs` | `12` | `build --jobs` |
| `use_cache` | `true` | 为 `true` 且变量已设置时传入 `--reference` / `--depot-tools`；都未设置则在线下载并给出警告 |
| `draft_release` | `true` | 为 `false` 时不创建 Release，只把完整发布集合（含约 200 MiB 的 ZIP）上传为工作流 artifact；公开仓库的 artifact 任何登录用户都能下载，见第 8 节 |
| `keep_workspace` | `true` | 成功后保留构建工作区；为 `false` 时由 `cleanup` 删除 |
| `resume_run_id` | 空 | 续用另一次失败运行的构建工作区，见第 6 节 |

`--ref` 决定源码提交：草稿 Release 的目标提交就是该运行的提交（`GITHUB_SHA`），发布时 GitHub 在这个提交上创建标签。

编译阶段 Actions 日志可能数小时没有新输出，这是正常的：Ninja 输出写在工作区 `logs/` 中。可在构建机上随时查看进度：

```powershell
python fp-kernel/scripts/release.py status --workspace E:\fp-ci\<run id>\build
```

## 6. 失败与续跑

失败时工作流会执行 `status` 打印最后一步和日志尾部，并上传报告 artifact：`doctor.json`、`.fp-build-state.json`、`source-verification.json`、`toolchain-verification.json`、打包清单、验收日志，失败时还包括工作区 `logs/` 下的全部日志。构建工作区始终保留，工作流不会删除失败的工作区。

- **同一运行重试**：修复原因（网络、工具版本、磁盘等）后，在运行页面点 **Re-run failed jobs**。run id 不变，工作流自动续用 `<run id>\build`：若源码校验已经通过，则跳过 `prepare`，直接 `build`（Ninja 续编译）；否则执行 `prepare --resume`，跳过已成功的步骤。打包、验收和发布集合写入新的 `attempt-<n>`。
- **新运行续用旧工作区**：触发时填写 `resume_run_id=<失败运行的 run id>`。新运行的输出写在自己的 `<run id>\attempt-<n>` 下。
- **续跑条件**：同一台机器、相同的 runner 工作目录、相同的锁定清单（锁定清单改变会被 `release.py` 拒绝）、相同的 `use_cache` 设置和缓存变量、相同的工具链路径。`release.py` 发现已成功步骤的命令发生变化时会拒绝续跑，此时应不填 `resume_run_id` 重新运行，使用新工作区。
- **首次 clone/checkout 失败**留下部分目录时，先在构建机上执行 `repair-checkout`（见 [构建迁移与发布](构建迁移与发布.md) 第 4 节），再重试。
- **补丁冲突**不要反复重试，先分析日志。
- **验收失败**时查看报告中的 `validation-*.log`（字体、桌面会话等），不能手工修改报告。重试会在新的 `attempt-<n>` 中重新打包和验收。

## 7. 审核并发布草稿

1. 从运行摘要中的链接打开草稿，或执行 `gh release view <tag> --repo TgolMsk/fingerprint-electron`。草稿只对有写权限的人可见。
2. 核对发布说明中的 Electron、Chromium、FP Kernel 版本和源码提交；`.validation.json` 中 `passed` 为 `true`、四项检查的 `exitCode` 均为 `0`、`archiveSha256` 与 ZIP 一致；`SHA256SUMS` 覆盖其余 6 个文件。可下载到本地复核，必要时在另一台机器试装：

   ```powershell
   gh release download <tag> --repo TgolMsk/fingerprint-electron --dir review
   ```

3. 发布：在 Releases 页面编辑草稿并点 **Publish release**，或执行 `gh release edit <tag> --repo TgolMsk/fingerprint-electron --draft=false`。当前产物是 testing 配置，可同时加 `--prerelease`。发布后，说明中的资产下载链接才生效。
4. 不打算发布时，在 Releases 页面删除草稿。草稿尚未创建标签，删除不影响仓库内容。
5. 如果 `release` 作业上传中途失败留下不完整的草稿，先删除该草稿，再对运行点 **Re-run failed jobs**；同一发布集合会重新校验 `SHA256SUMS` 后上传。

## 8. 安全须知

- 仓库公开且使用自托管 runner：任何能让工作流在该 runner 上运行的人，都能在构建机上执行代码。本工作流只有 `workflow_dispatch`，只有具备写权限的协作者可以触发。**不要**为任何使用 `fp-kernel-builder` 或 `self-hosted` 标签的工作流添加 `pull_request`、`pull_request_target`、`push`、`issue_comment`、`workflow_run`、`schedule` 等触发器，也不要新增其他以自托管 runner 为目标的工作流。
- fork 的 pull request 可以**在 PR 里自带一个新工作流文件**，把 `runs-on` 写成本机的标签；只修改本工作流的触发器挡不住这种情况，唯一的闸门是批准设置。在 **Settings → Actions → General** 的 fork pull request 工作流设置中选择 **Require approval for all external contributors**（旧界面措辞为 outside collaborators），并且**不要批准**修改了 `.github/` 的外部 PR 的工作流运行。
- 不构建时停止 runner 服务（`Get-Service 'actions.runner.*' | Stop-Service`），触发构建前再启动，可进一步缩短构建机暴露在外的时间。
- 有写权限的人可以在任意分支修改工作流后手动触发，这等同于在构建机上执行代码。只给可信维护者写权限，并对默认分支和 `.github/` 启用分支保护或代码所有者审查。
- runner 使用专用标准账号，不加入 Administrators；构建机上不存放与本项目无关的凭据，不要用该账号登录个人 GitHub CLI（工作流使用每个作业自动签发的 `GITHUB_TOKEN`）。
- 令牌范围：工作流默认权限为 `contents: read`。只有两个短作业拿到 `contents: write`：`check-tag`（草稿 Release 只对有推送权限的令牌可见，编译前的占用检查因此需要写权限）和 `release`（创建草稿）。运行数十小时、执行上游下载钩子和验收程序的 `build` 作业只有只读令牌；`GH_TOKEN` 只出现在调用 `gh` 的两个步骤的环境里；检出使用 `persist-credentials: false`，令牌不会写进构建机上的 `.git/config`。
- 第三方 action（`actions/checkout`、`actions/upload-artifact`）固定到完整提交 SHA，行尾注释标明对应版本（checkout v6.1.0、upload-artifact v6.0.0，均为 Node 24，需要 runner ≥ 2.327.1，保持 runner 自动更新）；升级时核对新版本的发布说明后再替换 SHA。
- 所有输入都通过环境变量传入脚本并先做格式校验，不直接拼接进脚本文本。
- **公开可见的内容**：公开仓库的运行日志、步骤摘要和工作流 artifact 对所有人可见，artifact 任何登录 GitHub 的用户都能下载。报告 artifact 含构建机路径、runner 名称和构建日志；`draft_release=false` 时上传的完整发布集合（含运行时 ZIP）也会在审核前就可被下载。只有草稿 Release 仅对有写权限的人可见。
- 发布内容：`.validation.json` 含构建机上的绝对路径，`FP_WORK_ROOT` 不要使用含个人信息的路径。源码 ZIP 由 `release-set` 按白名单生成，已排除本机配置、证书和密钥。
- runner 默认自动更新；构建机的 Windows 补丁仍需定期安装。

## 9. 下游应用使用已发布运行时

下游应用（例如 RolesTab）按以下方式获取和安装运行时：

1. **固定版本和校验值。** 在应用配置中记录审核后的标签、ZIP 名称和 SHA256（见发布说明）。同一个 Release 里的 `.sha256` 只能证明传输完整，不能代替你自己固定的值。
2. **下载三件文件到同一目录**：ZIP、`.sha256`、`.validation.json`。

   ```powershell
   $Tag = 'v44.4.5-fp0.1.0-testing.2'
   $Name = 'fp-electron-44.4.5-fp0.1.0-win32-x64-testing.zip'
   gh release download $Tag --repo TgolMsk/fingerprint-electron --pattern "$Name*" --dir downloads
   # 不使用 gh 时，从 https://github.com/TgolMsk/fingerprint-electron/releases/download/$Tag/<文件名> 分别下载三件文件
   ```

3. **校验。**

   ```powershell
   $Expected = '<应用中固定的 SHA256>'
   $Actual = (Get-FileHash -Algorithm SHA256 -LiteralPath "downloads\$Name").Hash.ToLowerInvariant()
   if ($Actual -ne $Expected) { throw "SHA256 不匹配: $Actual" }
   $Recorded = ((Get-Content -LiteralPath "downloads\$Name.sha256" -Raw).Trim() -split '\s+')[0]
   if ($Recorded -ne $Actual) { throw '.sha256 与 ZIP 不一致' }
   ```

4. **安装。** 使用同一标签的 `release.py`（本仓库该标签的检出，或 Release 中的 `fp-lab-source-*.zip`），需要 Python 3.11 或以上：

   ```powershell
   python fp-kernel/scripts/release.py install-runtime --archive (Resolve-Path "downloads\$Name").Path --project D:\apps\RolesTab
   ```

   `install-runtime` 要求 `.sha256` 和 `.validation.json` 与 ZIP 位于同一目录，会再次核对整包、逐个文件、内嵌锁定清单和四组验收结果，解压到 `<project>\runtime\<包名>-<SHA256 前 12 位>\`，启动一次隐藏进程检查实际版本和指纹接口，最后原子更新 `<project>\runtime\current.json`；下游应用读取其中的相对路径 `executable` 启动 Electron。任何一步失败都不会切换当前运行时。需要回退时执行 `python fp-kernel/scripts/release.py rollback-runtime --project D:\apps\RolesTab`。

不要只复制 `electron.exe`；发行包内的配套文件、语言文件和许可证必须保留。

## 10. 磁盘清理

- `keep_workspace=true`（默认）保留 `<run id>\build`，可以作为下一次的 `FP_REFERENCE_CACHE`。
- `keep_workspace=false` 时，只有 `build`、`reports` 和 `release`（或未启用的 `release`）全部成功，`cleanup` 作业才删除本次使用的构建工作区（续跑时是被续用的那个 `<run id>\build`）。删除前检查路径必须是 `<FP_WORK_ROOT>\<数字 run id>\build`、不是链接、含 `.fp-build-state.json`，并使用不跟随目录链接的 `rd /s /q`。它不会删除 `attempt-*` 输出、缓存目录或其他任何目录。
- `attempt-*` 目录（验收目录含解压后的运行时和应用副本，发布目录含两个 ZIP）在确认发布后由维护者手动删除；失败运行的工作区也由维护者决定续跑或删除。
