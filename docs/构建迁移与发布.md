# 可迁移构建、运行时发布与内核升级

本流程支持 Windows x64。核心入口是 `fp-kernel/scripts/release.py`，锁定清单是 `fp-kernel/build/lock.json`。它将源码、工具链、补丁和发行文件连接起来；实际验证结果见 [构建发布验证报告](../fp-kernel/reports/release/REPORT.md)。

换机器只开发界面、SDK 或运行应用时，使用已发布的运行时包即可。只有修改 C++ 内核或升级 Electron/Chromium，才需要完整编译环境。

## 1. 当前固定版本

| 项目 | 锁定值 |
| --- | --- |
| Electron / Chromium | 44.4.5 / 152.0.7977.130 |
| 内置 Node.js / FP Kernel | 24.21.0 / 0.1.0 |
| 构建机 Node.js / Python / Git | 22.23.2 / 3.14.5 / 2.55.0.windows.5 |
| 构建脚本实际使用的 depot_tools Python | 3.11.8 |
| Visual Studio 工具集 / MSVC | 2026 / 14.50.35717 |
| Windows SDK | 10.0.26100.0 |
| Clang | llvmorg-23-init-19482-g53d18800-1 |
| Rust | 精确版本字符串记录在锁定清单的 `toolchain.rustVersion` |
| GN 配置 | `testing.gn`，`symbol_level=0`，`blink_symbol_level=0`，x64 |

当前产物是 **testing 配置的运行时**，不是已验证的优化 release 配置，也不是安装器。普通应用开发接口与 Electron 一致，额外提供 `Session.setFingerprintConfig`；打包时必须使用此定制运行时。

锁定清单记录 159 个源码仓库的原始提交及应用补丁后的 Git tree、depot_tools 提交、4 个 Electron 补丁和 12 个 Chromium 补丁的 SHA256。GN、CIPD 和其他下载工具的引用由这些固定版本的 DEPS 与下载脚本决定。构建还检查 Clang、Rust、Python、MSVC 和 SDK。

项目和内核仓库的 `.gitattributes` 禁止 Git 转换补丁和 `build/lock.json` 的字节，避免 Windows `autocrlf` 改变 SHA256。其他 JSON 文件采用 LF；锁清单按已验证的原始字节保存，以保持已有运行时内嵌锁的校验值一致。

补丁基线使用 Electron 的 `refs/patches/upstream-head`。**不能使用 `.gclient_previous_sync_commits` 作为基线**：它可能保存已应用补丁的提交，重复应用会冲突。

## 2. 换机器运行或继续二次开发

本次发布为 [v44.4.5-fp0.1.0-testing.1](https://github.com/TgolMsk/fingerprint-electron/releases/tag/v44.4.5-fp0.1.0-testing.1)，提供 Windows x64 运行时、源码附件、校验清单和验收记录。下载命令及 electron-builder 接入说明见 [运行时下载与接入](运行时下载与接入.md)。GitHub Releases 是文件分发渠道，不代表产物采用优化 `release` 编译配置；本次仍为 `testing` 配置。

准备源码发行包以及以下文件，放在任意目录：

```text
fp-electron-44.4.5-fp0.1.0-win32-x64-testing.zip
fp-electron-44.4.5-fp0.1.0-win32-x64-testing.zip.sha256
fp-electron-44.4.5-fp0.1.0-win32-x64-testing.zip.validation.json
```

在解压后的项目根目录运行，`$Archive` 改成下载文件的实际位置：

```powershell
$Archive = (Resolve-Path '.\downloads\fp-electron-44.4.5-fp0.1.0-win32-x64-testing.zip').Path
python fp-kernel/scripts/release.py install-runtime --archive $Archive
.\启动指纹测试.cmd
```

安装命令先核对整个 ZIP、每个文件、内嵌锁定清单及该 ZIP 的四组验收结果，再解压到项目 `runtime/版本-校验值/`，启动一次隐藏进程检查实际版本和原生指纹接口，最后原子更新 `runtime/current.json`。任何前置失败均不会切换当前运行时。重复安装到同一目录会拒绝覆盖；已打开的程序需正常退出并重新启动才能切换。

安装/验证脚本需要 Python 3.11 或以上；完整编译则要求上表锁定版本。完成安装后双击运行不需要 Python、Node.js 或编译工具。开发和运行测试需要 Node.js。不要只复制 `electron.exe`，需保留发行包内的配套文件、语言文件和许可证。

启动器解析顺序：

1. 环境变量 `FP_DEMO_ELECTRON`。
2. 项目 `runtime/current.json` 的相对 `executable`。
3. 本机 `.fp-local.json` 的 `electron`。
4. 项目 `runtime/electron.exe`。

例如不安装而直接测试一个已解压目录：

```powershell
$env:FP_DEMO_ELECTRON = (Resolve-Path '.\downloaded-runtime\electron.exe').Path
node fp-demo/scripts/start.js
```

`.fp-local.json` 仅供开发机使用，已加入忽略规则且不会进入源码发行包：

```json
{
  "electron": "runtime/electron.exe",
  "source": "../electron-build/src"
}
```

源码、`fp-demo`、`fp-sdk`、根目录 `scripts` 应一起迁移。源码发行包不携带登录数据。账号数据与扩展登记的跨路径迁移仍须按 [使用手册](项目使用手册.md) 备份处理；运行时切换不承担 Chromium 用户数据降级恢复。

## 3. 在新目录重建同一版本

### 前置工具

安装锁定的 Node.js、Python、Git，准备合法取得的对应 MSVC 和 Windows SDK。工具链目录应包含：

```text
VC/Tools/MSVC/14.50.35717/
Windows Kits/10/Include/10.0.26100.0/
Windows Kits/10/Lib/10.0.26100.0/
```

如果 Visual Studio 和 Windows SDK 分开安装，可在 `doctor`、`prepare`、`build` 增加 `--windows-sdk <Windows Kits/10 目录>`；PowerShell 入口对应 `-WindowsSdk`。不传时采用上面的合并工具包布局。检查器还会核对已安装 VS 的默认 MSVC 工具集，避免同机存在多个工具集时误用其他版本。

本次实际使用的是 Chromium 下载的 VS2026 工具包，不是此前环境说明中的 VS2022。脚本不会静默替换版本或修改系统安全配置。新机器的 Microsoft 工具链获取、许可与安装由机器所有者完成；未验证“一键安装全套工具链”。完整 Chromium 源码和编译产物需要大量磁盘、内存及下载时间。

以下变量是示例位置，应改为新机器的实际目录。构建根目录必须为空；不要指向已有开发源码。

```powershell
$BuildRoot = 'E:\builds\fp-44.4.5'
$Toolchain = 'E:\toolchains\vs2026'
python fp-kernel/scripts/release.py doctor --windows-toolchain $Toolchain
python fp-kernel/scripts/release.py prepare --workspace $BuildRoot --windows-toolchain $Toolchain
if ($LASTEXITCODE -ne 0) { throw '源码准备失败，请查看工作目录 logs' }
python fp-kernel/scripts/release.py build --workspace $BuildRoot --windows-toolchain $Toolchain --jobs 12
if ($LASTEXITCODE -ne 0) { throw '构建失败，请查看工作目录 logs' }
```

在线准备会获取固定 depot_tools 与 Electron，使用固定 DEPS 同步依赖、执行上游下载钩子，并核对最终源码 tree。同步失败或得到不同源码会阻止编译。网络依赖仍受上游服务可用性影响；固定提交不等于永久离线可用。

已有一台构建机时，可使用其源码与下载缓存，减少重复下载：

```powershell
$CacheRoot = 'E:\existing-electron-build' # 此目录的 src 子目录是 Chromium
$DepotCache = 'E:\tools\depot_tools'
python fp-kernel/scripts/release.py prepare --workspace $BuildRoot --reference $CacheRoot --depot-tools $DepotCache
if ($LASTEXITCODE -ne 0) { throw '源码准备失败' }
python fp-kernel/scripts/release.py build --workspace $BuildRoot --jobs 12
```

缓存方式创建独立 Git 检出，只复制指定构建依赖，**不复制 `out/`、旧对象文件、旧 EXE 或账号数据**。本地 Git 对象可以由 Git 硬链接复用；源码工作树、索引与构建输出独立。所有补丁重新应用，所有源码 tree 重新核对。这验证干净源码与干净输出重建；不等于全新 Windows 虚拟机和完全无缓存下载验收。

输出在 `$BuildRoot/src/out/FPTesting`。构建时重新生成 GN 参数、版本头文件和 `build/win_toolchain.json`；后者可含该机器的绝对工具链路径，属于本地生成文件，不写进共享源码清单。源码流程不再依赖 `e use` 配置或某个固定盘符。

新工作区会保留 Git 与已复制下载依赖的 `.gclient_entries` 登记，之后可继续作为另一台机器或另一份空目录的 `--reference` 缓存。缓存链路不包含旧编译输出。

## 4. 失败、恢复与日志

每次执行记录 `.fp-build-state.json`、`logs/`、`source-verification.json`、`toolchain-verification.json`。可随时只读查看状态：

```powershell
python fp-kernel/scripts/release.py status --workspace $BuildRoot
```

显示当前步骤、日志尾部和本轮 Ninja 已完成/总步骤；续编译会重新计算本轮剩余任务，因此该比例不是端到端耗时百分比。

所有原生命令检查退出码，首次失败立即停止。不会重置原开发树、自动修改 `VERSION` 或切换正在使用的运行时。

相同锁定清单、相同参数的准备过程可续跑：

```powershell
python fp-kernel/scripts/release.py prepare --workspace $BuildRoot --reference $CacheRoot --depot-tools $DepotCache --resume
```

成功完成的命令会跳过，已存在缓存文件必须与来源校验一致。更换锁定清单或已完成步骤的命令参数必须新建工作目录；续跑不会重新执行参数已改变的成功写操作。编译失败后修复工具或外部条件，重新执行 `build`，Ninja 可续编译。

如果首次 Git clone 或 checkout 已以非零退出码失败，留下的部分目录阻碍续跑，可指定日志中的仓库：

```powershell
python fp-kernel/scripts/release.py repair-checkout --workspace $BuildRoot --repository src/third_party/litert/src
# 再执行上面的 prepare --resume
```

该命令只允许处理有明确失败记录的首次 clone 或 checkout，支持已锁定源码仓库及 `tools/depot_tools`。整个部分目录会保留到 `failed-checkouts/`，随后由 `prepare --resume` 重新检出，不删除文件。仍在运行、没有退出码记录或已经成功检出的仓库均拒绝修复。

补丁冲突会保留 Git am 状态与日志。不要反复盲目 `--resume`；先分析日志。版本适配应在候选工作区完成并重新导出补丁，再用新目录验证；自动恢复不会跳过冲突补丁或将失败误报为成功。

已安装过两个版本后，可以回到上一运行时：

```powershell
python fp-kernel/scripts/release.py rollback-runtime
```

回退前会核对上一运行时能启动且版本匹配。这里只回退运行时选择；用户数据要先备份，用新版本写入后的 Chromium 数据不保证可被旧版本读取。首次安装没有上一版本指针。

## 5. 打包、验收和准备发布

可以用 PowerShell 总入口顺序执行准备、编译、打包、验收和发布集合生成，任一步失败立即退出：

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File fp-kernel/scripts/release.ps1 `
  -Root $BuildRoot -ValidationRoot 'E:\validation\fp-44.4.5' `
  -ArtifactDir dist/runtime -ReleaseDir dist/release-44.4.5-fp0.1.0 `
  -WindowsToolchain $Toolchain
```

已有独立准备目录时加 `-Prepared`；继续同一准备过程用 `-Resume`。包输出和验收目录必须是新位置。也可分步执行，每一步都应检查 `$LASTEXITCODE`：


```powershell
python fp-kernel/scripts/release.py package --build-dir "$BuildRoot\src\out\FPTesting" --output dist/runtime
$Archive = (Resolve-Path '.\dist\runtime\fp-electron-44.4.5-fp0.1.0-win32-x64-testing.zip').Path
python fp-kernel/scripts/release.py verify-package --archive $Archive
python fp-kernel/scripts/release.py validate-release --archive $Archive --workspace 'E:\validation\fp-44.4.5'
if ($LASTEXITCODE -ne 0) { throw '验收未通过，不能准备发布' }
python fp-kernel/scripts/release.py release-set --archive $Archive --output dist/release-44.4.5-fp0.1.0
```

打包从官方 `electron_dist_zip.runtime_deps` 获取发行文件并遵循 Electron 的排除规则，避免带上 obj/PDB/完整源码。包名包含 Electron、FP Kernel、系统架构和配置；内嵌 `runtime-manifest.json` 与 `build-lock.json`，提供逐文件大小/SHA256、编译实际版本、原生指纹 API 探测和源码 tree。外部 `.sha256` 用于整包传输完整性检查。

对本流程管理的构建目录，打包还要求成功记录中的输出目录、GN 参数与官方 `dist.zip` 校验值一致，并逐一核对待打包文件与官方 ZIP 的内容；误选其他输出目录或构建后修改参数、发行 ZIP、运行时文件都会中止。

`validate-release` 将包解压到新的目录，再复制不含本机配置和旧运行时的应用源码，依次运行内核、三账号、工作台和 SDK 四组验收。任一失败不生成成功结论。字体断言依赖测试机器已安装的字体，失败需分析测试日志，不能手工把报告改为成功。

`release-set` 要求 **当前锁定清单、该 ZIP 的 SHA256、应用及验收源码摘要、四组成功验收** 一致，然后输出运行时 ZIP、校验文件、验证报告、运行时清单、源码 ZIP、`source-manifest.json` 和 `SHA256SUMS`。源码 ZIP 保留补丁、脚本、SDK、工作台、说明文档，排除缓存、本机配置、账号数据、本机 HTTPS 测试证书与密钥。默认四组验收不需要这些证书；如运行额外的 consistency HTTPS 手动测试，请在本机重新生成证书。`source-manifest.json` 记录源码 ZIP 及逐文件校验值，打包后会回读验证。源码快照应在代码评审后关联 Git 标签。

SHA256 检查提供完整性验证，不能替代可信下载来源或发布者数字签名。当前流程没有 Windows 代码签名、安装器签名或可证明的逐字节可复现构建；相同锁定版本的不同构建可能有不同 PE 时间信息和 ZIP 时间戳。

## 6. 放到 GitHub

首个公开运行时标签为 `v44.4.5-fp0.1.0-testing.1`，标记为 **Pre-release**。发布时先从标签目标提交生成源码附件、校验运行时并完成验收，将全部附件上传到草稿并检查远端大小/SHA256，最后公开预发布版。`release-provenance.json` 记录发布提交和验证范围，`release-validation-logs.zip` 保存本次日志。后续版本使用新标签，不覆盖已发布版本。

公开仓库为 [TgolMsk/fingerprint-electron](https://github.com/TgolMsk/fingerprint-electron)，统一提交应用源码、SDK、补丁、锁定清单、脚本和报告。`.gitignore` 排除 `runtime/`、`dist/`、本机配置、密钥和构建缓存。完整 Chromium/Electron 源码工作区放在项目外面。公开仓库中的 `fp-kernel/` 是完整源码目录，不是子模块；原开发机的内层 Git 历史保留在本机，不随公开快照上传。

运行时与源码发行 ZIP 放在 GitHub Releases，不加入 Git 历史。当前运行时 ZIP 约 201 MiB，具体以清单为准。所有大文件上传前先准备完整发布集合，再由维护者发布：

```powershell
# Repo、Tag、ReleaseDir、NotesFile 必须指向你自己的已确认仓库/标签/文件。
$Assets = Get-ChildItem -LiteralPath $ReleaseDir -File | ForEach-Object FullName
gh release create $Tag @Assets --repo $Repo --verify-tag --draft --title $Tag --notes-file $NotesFile
```

这个示例只创建草稿；审核内容后再在 GitHub 发布。`release.py` 本身不会推送源码、创建远端标签、上传文件或公开发布。适合由有足够磁盘和已安装锁定工具链的 Windows 构建机运行。

### 用 GitHub Actions 自托管 Runner 构建草稿 Release

仓库提供只能手动触发的工作流 `.github/workflows/build-runtime.yml`。它在维护者自己注册、带 `fp-kernel-builder` 标签的 Windows x64 自托管 runner 上，依次执行本文第 3–5 节的 `doctor`、`prepare`、`build`、`package`、`verify-package`、`validate-release`、`release-set`，再用 `gh release create --draft` 把发布集合创建为草稿 Release，仍由维护者审核后发布。GitHub 托管 runner 的磁盘和单作业时长不足以完成编译。

runner 注册、仓库变量、触发与续跑、审核发布、安全设置，以及下游应用如何下载、校验和安装运行时，见 [自托管构建流水线](自托管构建流水线.md)。

## 7. 升级到新的 Electron

同版本换机器可以按锁定清单重建。跨版本升级仍需要审查 Chromium/Electron 变更、适配 C++ 补丁并重新测试，不能保证零冲突。

1. 用 `upgrade-plan --to vX.Y.Z --output upgrade-plan.json` 解析明确的目标标签和提交；该命令不修改当前锁、源码或运行时。
2. 在新的候选源码目录同步目标版本；应用并适配有序 FP 补丁，首次冲突就停。保留现有发布版本。
3. 更新候选模板中的 runtime/toolchain、补丁顺序和版本；补丁导出到评审目录，检查 diff，提交候选源码。
4. 使用下面的 `capture-lock` 生成新的候选清单。该入口只写新文件，不覆盖现有锁；工具链版本必须在模板中明确填写。
5. 使用候选清单在另一个空目录 `prepare`、`build`、`package`、`validate-release`、`release-set`。所有命令在 action 前加 `--lock <候选清单>`。
6. 评审代码与报告，再更新项目正式锁和 `VERSION`、创建发布标签。用测试数据确认升级后再切换正式账号环境。

```powershell
python fp-kernel/scripts/release.py --lock candidate-template.json capture-lock `
  --workspace $CandidateRoot --depot-tools $DepotCache `
  --electron-base vX.Y.Z --chromium-fp-base $BeforeFpCommit --chromium-p2-base $BeforeP2Commit `
  --output candidate-lock.json
```

`capture-lock` 从当前 `.gclient_entries` 找到实际 Git 仓库，从 Electron 保存的 upstream ref 获取原始基线，重新计算补丁 SHA256 和最终源码 tree。它不自动判断补丁逻辑正确；这由独立重放、编译与验收证明。

`apply.ps1`、`check-env.ps1`、`export.ps1`、`upgrade.ps1` 均已改为上述流程的入口。`upgrade.ps1 -To` 必须匹配传入清单的 Electron 版本，失败不会更新版本。`export.ps1` 只向新目录导出 Chromium/Electron 汇总 diff 供评审，不覆盖现有有序补丁；这些原始 diff 不能直接替代 `git am` 格式的补丁序列。

参考：[Electron 官方 GN 构建说明](https://www.electronjs.org/docs/latest/development/build-instructions-gn)、[Electron build-tools](https://github.com/electron/build-tools)。
